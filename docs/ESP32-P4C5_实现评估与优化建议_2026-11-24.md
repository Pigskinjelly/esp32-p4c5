## 二、功能完整性

### 2.1 【P2·已证实】三个能力的 UI 被删，逻辑还在（用户改不了）

| 能力 | 现状 | 证据 |
|---|---|---|
| 待机/息屏时间 | 设置页已无入口，`idle_btn_cb` **0 次引用** | `ui_app_settings.c:170` 定义、无 `add_event_cb`；设置页行清单只有 Wi-Fi/存储/内存/运行时间/音量/屏幕方向/应用管理/重启（`:595-677`） |

| 蓝牙开关 | 设置页删除，但控制中心有 `s_cc_bt_sw` → **可达**（可接受） | `ui_shell.c` |

判定：这是"删 UI 留逻辑"的中间态。**分辨率/帧率、待机时间**目前用户无法设置，只能吃默认值（1280×720@30、`IDLE_DEFAULT_S`）。若产品决定不再暴露，应把 4 个死回调与 `s_res_btns`/`s_idle_vals` 一起删掉；若要保留，10 行 UI 就能挂回去。

### 2.2 【P1·已证实】BLE「位置回传」服务是半接线

- 有完整 GATT 定义（`bt_mgr.c:134-140`，自定义 128 位 UUID）、解析、回调 `s_loc_cb(lat, lon)`（`:127-128`）；
- 但 `bt_mgr_set_loc_cb()` 在整个工程**没有任何调用方**（`grep` 仅命中定义与 `#else` 桩），坐标写进来后无人消费。
- 代价：517 行代码 + NimBLE 主机栈内存 + C5 射频常开；用户侧只看到"蓝牙开关能开"。

判定：要么接上一个真实用途（如手机靠近亮屏/防丢/配网），要么整块删除。**不建议继续留着"能连但没用"的服务**——它会让人以为功能已具备。

### 2.3 【P2·需产品确认】导航 App 冻结后的空位

`ui_apps.c` 只注册 7 个（监控/相机/相册/交易/音乐/天气/设置），地图源码在 `docs/frozen/map-app/ui_app_map.c.frozen`，`main.c:539-547` 还留着 `ui_map_selftest` 的悬空声明（`#if 0` 内）。桌面功能位从 8 个变 7 个，需确认是"永久砍"还是"等重做"。

### 2.4 其他既有缺口（沿用前两轮，未变）

- RTSP 无鉴权（同网段可看画面）；

- 分时图已整体移除（**trend 相关 0 命中，无死代码残留，这点做得好**），需确认是否永久放弃。

## 三、性能

### 3.1 【P1·已证实】行情区每秒"无条件重刷"，休市时纯空转

`apply_data()`（`ui_app_stock.c`，由 1 s 行情回调置 `s_dirty` 后执行）每秒对**全部**控件重新格式化并写入：

- 指数 4 ×（`set_text_fmt` ×2 + `set_style_text_color` ×2）
- 自选 8 ×（`set_text`/`set_text_fmt` ×3~4 + 颜色 ×2）
- 再调 `detail_refresh()` 与 `alist_price_refresh()`。注意 `detail_refresh()` 只判 `s_visible && s_detail`，**不判详情面板是否隐藏**——停在自选列表时仍每秒格式化 10 个 label（不产生重绘，但白耗 CPU 与 label 文本重分配）

合计约 **50 次 label 写入 + 24 次样式写入/秒**，**不比较新旧值**。收盘后价格完全不变，这些 invalidate 全部是白干：按每 label 约 1,200 px 估算，约 6 万 px/s 的重绘，占 480×480 全屏的 ~26%/秒。叠加 30 fps PPA + H.264 硬编 + SDIO 收包，这部分是可以直接省掉的。

同一模式在时钟区更明显：`tick()` 每秒调 `lv_label_set_text(s_lbl_status, st)` 与 `set_style_text_color(..., col(color))`（`ui_app_stock.c` tick 前 20 行），文本、颜色多数秒内不变。

### 3.2 【P1·已证实】字库占固件一半、常驻 PSRAM

- 2,755 KB / 5,546 KB = **49.7%**；固件/分区 = 66%，**没有 OTA 分区**（单 factory 8 MB）。
- 字库符号落在 `0x4820xxxx`（PSRAM 段）→ 运行期常驻 PSRAM，同时占 flash 与 PSRAM 两份预算。
- 构建成本：6 个巨型 C 文件 → 全量 38 分钟，改一个汉字要重编 100k 行。

这不是"能不能跑"的问题，而是**以后加任何功能都要和字库抢空间**（再加 1 MB 就撞 8 MB 上限）。

### 3.3 【P2·已证实】LVGL 刷新周期 15 ms（66 fps 目标）

`sdkconfig:3310 CONFIG_LV_DEF_REFR_PERIOD=15`。UI 绝大多数时间是静态的，30 ms（33 fps）对这块方屏的观感差异很小，但 `lv_timer_handler` 的调用频率直接减半。需实测动画/滑动是否可见差异。

### 3.4 【P2·已证实】K 线每次全画布重绘

`kline_redraw()`（`ui_app_stock.c:1530-1695`，165 行）：`kfill` 清 392×204×2 = **160 KB**，再逐像素画 ~80k 像素。触发点包括：数据到达、按下/拖动/松手（`PRESSING` 每次移动都可能重绘）。网格和刻度是静态的，却每次重画。

### 3.5 【P2·推断】内部 DMA 仍紧，碎片是 SDIO assert 的温床

min 85 KB 比之前（33 KB）健康很多，但 R-30 的根因是**碎片化导致按批长度申请失败**，不是总量不足。当前心跳只报 `free`/`min`，**不报 `largest_block`**，无法判断碎片。建议加一个 `heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL|MALLOC_CAP_DMA)` 到心跳。

### 3.6 【P3】其他

- RTSP 请求**逐字节** `recv`（`rtsp_server.c:308-320`），每请求约 200 次系统调用；
- `runlog` 每 2 s `fflush` 到 TF（低优先级任务，设计合理），但**队列深度与丢弃计数未见**，卡慢时可能积压；
- 无 CPU 占用观测：`CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS` 未开，无法量化上面几条。

## 四、可维护性

### 4.1 【P1】`ui_app_stock.c` 4,130 行，单文件承载一个子系统

一个文件里同时有：3 个市场的自选/指数模型、行情抓取与解析（4 个源）、详情页、K 线绘制、提醒、资讯、拼音输入联动。改任一处都要在 4,130 行里找锚点，且**每次改动都触碰同一文件的 8 个调试导出函数**。这是当前最大的维护风险（不是 bug，是"以后没人敢动"）。

### 4.2 【P1】三市场逻辑三份拷贝

`A_IDX_DEF` / `US_IDX_DEF` / `HK_IDX_DEF`（`:68/72/75`）、`A_WATCH_DEF/US/HK`（`:229/233/237`）、`trade_status_a/hk/us`（`:124/141/156`）、以及 `list_load/save`、`code_to_secid`、`em_candidates` 里的市场分支——`grep` 命中 **31 处**。四份表 + 三份状态机 + 三处分支，本质是**同一套"市场"抽象没抽出来**。

### 4.3 【P1】字库产物入库（18 MB / 184k 行）

`ui_font_cjk_16/24(_extra).c`、`ui_font_time_96(_light).c` 都在 `main/`，每次改字表都产生 10 万行级 diff（本次未提交改动就是 102,494 行）。后果：code review 失效、merge 冲突不可解、仓库体积膨胀。应入库**字表（txt）+ 生成脚本**，产物由构建时生成（或 CI 生成后发布）。

### 4.4 【P2】样式常量未收敛

`ui_theme.h` 只有 9 个语义色（`C_BG`/`C_ACCENT`/`C_UP`…），但业务代码里裸 `0xRRGGBB` 有：`ui_app_stock.c` **39 个**、`ui_shell.c` **45 个**（去重后）。同一套"卡片深蓝"在不同文件里有 3~4 个近似值，调色/换主题等于全库搜索。

### 4.5 【P2】网络层各自为政

`esp_http_client_init` 共 **8 处**（stock 2、music 3、weather 2、trade_day 1），每个都自带 timeout/buffer/UA/重试策略；解析器 4 套（东财/腾讯/新浪/天气 JSON）。想统一加"断网快速失败""统一 UA""统一重试退避"要改 8 个地方。

### 4.6 【P2】零测试、零静态检查

无 host 单测、无 `clang-tidy`、无 CI。而项目里恰好有一批**纯函数**极易测：`trade_day_*`（日期/节假日）、`snap_crop()`（画幅）、`kline_parse_*`（报文解析，历史上出过 `low` 字段错位）、`gbk_to_utf8`。这些是最该先补的。

### 4.7 【P3】死代码与调试残留

- 设置页 4 个死回调：`res_btn_cb`、`bt_switch_cb`、`idle_btn_cb`、`brightness_cb`（`ui_app_settings.c`）；
- 8 个 `ui_stock_debug_*` **无条件编译**（`ui_app_stock.c:3575` 起），仅调用点在 `#if STK_SELFTEST 0`；
- `main.c:539-547` `ui_map_selftest` 悬空声明 + `#if MAP_SELFTEST 0`；
- 根目录 `_t2.._t7.py/.log`（11 个文件）仍在工作区（已 ignore，但污染视野）。

### 4.8 【P3】重复的浮层/弹窗构建

stock 的 `build_add_modal`/`build_alert_edit`/`build_alert_list`、music 的搜索/收藏/下载浮层、gallery 的查看器，各自从零写定位、圆角、遮罩、关闭逻辑。`ui_theme` 已有 `ui_card`/`ui_label`，但**没有 `ui_modal`/`ui_sheet`**，导致每个 App 重写一遍。

## 七、建议落地顺序（为什么这么排）

```
今天      O-4（加观测）→ O-1（拿最大收益）→ O-2（一行）→ O-3（清死代码）
本周      O-9（先建安全网）→ O-6 第一步（只搬 net 层）→ O-8
下周      O-5（字库瘦身，配合覆盖率工具）→ O-6 全量拆分 → O-7
之后      O-10/O-11/O-12/O-13 按产品优先级
```

理由：
1. **O-4 先做**，否则 O-1/O-2 的收益无法证明（现在连 CPU 占用都看不到）；
2. **O-9 在 O-6/O-7 之前**，因为拆分和表驱动最容易"改坏但不报错"，需要单测兜底；
3. **O-5 放在结构性重构之后**：字库生成脚本变更会触发全量重编，和代码拆分混在一起会让"改坏了是谁的问题"无法归因；
4. O-7 的风险最高（交易时段判断），必须有新旧输出对照日志，不能只靠人眼。
