### 3.2 采纳关闭

**R-15（TCP 窗口 5,760）——同意不改。** 他们的理由"LWIP 缓冲走内部 RAM，App 打开后 heap_int 仅 ~55 KB，每连接 +27 KB 风险过高"成立；且现在实测**最低水位只有 33 KB**，把窗口拉到 32 KB 会直接把 SDIO 的致命路径（见 R-30）重新打开。建议保留为观察项：若将来做内存规划（R-10）再议，届时优先 16,384 并实测 RTSP 吞吐。

### 3.3 R-02 的技术裁决（他们提出反证，我逐条核过）

他们的反证（`开发交接文档` X.10 / `实施记录.md`）：*"NVS 已有 71 天缓存，说明旧代码至少成功写过一次，故'必然 assert'存疑，改动无害。"*

复核结果：**后半句（改动无害）成立，前半句的推理不成立。**

1. `holiday cache loaded: 71 day(s)` 是 `hol_load()`（读）打印的（`trade_day.c:235` 附近），只能证明**某个版本**写进去过，不含时间戳、不含写者身份；
2. 我在全部归档日志里检索 `calendar ready`（`fetch_all()` 在 `hol_save()` 之后才打印，`trade_day.c:407-410`）——**0 命中**。也就是说，**没有任何证据**表明"PSRAM 栈版本"成功走完过一次 `hol_save()`；
3. 反过来，机制是无条件的：`nvs_commit → esp_partition_write → esp_flash_write → g_flash_guard_default_ops.start`（IDF `flash_ops.c:82-86`）→ `assert(esp_task_stack_is_sane_cache_disabled())`（`cache_utils.c:127`），该函数要求 SP 在内部 DRAM（`:56-65`）。与工程代码无关，属 IDF 硬约束；
4. 结论：71 天缓存最可能由更早的构建（写盘调用点不同）留下；**当前代码若把写盘放回 PSRAM 栈任务，仍会 panic**。修复本身正确，且不依赖这个争论。

**建议（低成本防回归）**：把这条约束固化成脚本 `tools/check_psram_nvs.py`（扫 `xTaskCreate*WithCaps(..., MALLOC_CAP_SPIRAM)` 的任务体里是否出现 `nvs_*`/`esp_vfs_*_write`），进 CI 或 pre-commit。

### 3.4 R-08 与 R-30 的关系（重要）

`R-30-SDIO随机重启.md` 记录的 `assert failed: sdio_rx_get_buffer sdio_drv.c:953 (*buf)` → panic → `rst:0xc` 是**确凿的运行期重启真因**，有串口断言原文；他们据此做预分配 2×8 KB + 失败读掉丢弃，实测 110 s 崩 1~3 次 → 130 s 0 次。

但请注意两点，避免结论外溢：

- 这解释的是"**运行中** panic 重启"，**解释不了** R-01（上电后 `entry` 即崩、RA 在 bootloader、应用代码未执行）；
- 用户 V2.31 反馈的"点详情页重启"发生在 backtrace 关闭的版本上，**没有可比对的栈**，不能说"已被 R-30 修复"。
  → R-08 状态：**高概率相关、仍未闭环**，等真机复现一次即可定论（新固件已有 backtrace + 复位原因计数）。

### R-35【P2·已证实】"开 backtrace 就能定位 R-01" 的预期不成立

**证据**：R-01 的崩溃发生在 `entry 0x4ffac2ca` 之后、应用镜像加载前（`docs/audit-2026-11-19/serial_2026-11-19T1936.log:3-11`，`RA=0x4ffad3a2`）。`CONFIG_ESP_SYSTEM_NO_BACKTRACE` / `USE_FRAME_POINTER` 只影响 **app** 的 panic 处理；bootloader 阶段的崩溃由 ROM/bootloader 自带处理，仍只有寄存器 + Stack memory（这也是当时两次样本都只有寄存器转储的原因，而不是因为 `NO_BACKTRACE`）。

`实施记录.md:77` 写"若再出现，新固件会打出 `Backtrace:`，把日志给我即可定位"——**对 R-01 不成立**（对 R-08 那类 app 内 panic 成立）。

**修复（把诊断手段补对）**
1. `CONFIG_BOOTLOADER_LOG_LEVEL=4/5`（Debug/Verbose）跑 20 次冷启动，看崩在 `esp_image`/PSRAM 初始化/flash 探测哪一步；
2. A/B 变量：`SPIRAM_SPEED` 200M→120M、flash 80M→40M，各 20 次；
3. 记录每次的 `rst:0x` 序列与室温/供电（USB 口 vs 独立电源）；
4. 若仍无规律，用 `esptool --before no_reset` + 逻辑分析仪看 CHIP_PU/供电跌落。

**验证**：20 次冷启动 0 异常，或拿到可归因的 bootloader 日志段。
