# R-38 / R-39 / R-40：串口恢复后的三个实机问题

日期：2026-11-22
固件：2.39（`/d/p4c5b3`）

串口恢复后烧写并实测，暴露出三个必须修的问题。以下是现象、根因、修法与验证。

---

## R-38 开机即循环重启：`xQueueSemaphoreTake` 拿到 NULL 信号量

### 现象

烧写后串口每 ~2 秒重启一次，日志：

```
assert failed: xQueueSemaphoreTake queue.c:1709 (( pxQueue ))
Backtrace: 0x4ff2dab8 ... 0x4804a558
rst:0x4 (panic)
```

地址反解：

```
0x4804a558: fetch_task at main/ui_app_weather.c:223
```

### 根因

`ui_app_weather.c` 的任务启动顺序写反了：

```c
SemaphoreHandle_t sem = xSemaphoreCreateBinary();
if (sem) {
    xTaskCreateWithCaps(fetch_task, "wx_fetch", ...);   // 任务立刻抢占运行
    if (ok == pdPASS) {
        s_sem = sem;                                     // 这时才赋值 ← 太晚
    }
}
```

`fetch_task` 的优先级（3）高于创建者，创建成功后立刻开始跑，第一句就是
`xSemaphoreTake(s_sem, wait)`，而 `s_sem` 仍是 NULL → FreeRTOS 断言 panic。

这是上一轮做 R-36（任务创建失败兜底）时引入的回归：为了"创建成功才保留信号量"，
把赋值挪到了创建之后，反而制造了竞态。

交易 App 的 `stock_fetch` 是同样写法，只是开机没被触发，属于**潜伏的同类崩溃**。

### 修法

两处统一改成"先赋值、后创建；失败再回退"：

```c
s_sem = xSemaphoreCreateBinary();
if (s_sem) {
    if (xTaskCreate(...) != pdPASS) {
        vSemaphoreDelete(s_sem);
        s_sem = NULL;          // 保证任务不存在时不会留下悬空信号量
        ...
    }
}
```

### 验证

烧写后连续抓日志 60 秒：`assert failed` / `Guru` 计数 **0**，不再重启。

## R-39 开机直接连：NO_AP_FOUND 无法定位，扫描还被拒

### 现象

```
I wifi_mgr: country code CN: ESP_OK
W wifi_mgr: set band mode auto failed: ESP_ERR_WIFI_NOT_STARTED
I wifi_mgr: wifi started, auto-connect "<WiFi名称>"
W wifi_mgr: auto-reconnect "<WiFi名称>" #1 in 500ms (reason 210)
W wifi_mgr: scan start failed: 0x3006
```

两个问题：

1. `esp_wifi_set_band_mode()` 在 `esp_wifi_start()` **之前**调用 → 返回
   `ESP_ERR_WIFI_NOT_STARTED`，双频**根本没生效**。这个接口必须在 start 之后调。
2. 开机立刻 `esp_wifi_connect()`，WiFi 长期处于 connecting 状态，
   而 `esp_wifi_scan_start()` 在 connecting 期间会被拒（`0x3006` = `ESP_ERR_WIFI_STATE`），
   于是永远拿不到 AP 列表，"到底是没有这个网络还是密码错"无从判断。

### 修法

- `band mode` 移到 `esp_wifi_start()` 成功之后；
- 开机改成**先扫描、再按扫描结果决定是否连接**：
  扫完在 `WIFI_EVENT_SCAN_DONE` 里做判定——
  - 目标 SSID 不在列表 → 报错并列出可见 AP，**停止无意义重连**；
  - 目标在列表且是加密网络、但保存的密码为空 → 明确报"密码是空的"，停止重连；
  - 否则正常 `esp_wifi_connect()`。

### 验证

```
I wifi_mgr: country code CN: ESP_OK
I wifi_mgr: band mode: 2.4G + 5G          ← 双频生效了
I wifi_mgr: scan done: 5 unique AP(s)
E wifi_mgr: *** "<WiFi名称>" 是加密网络（auth=3），但 NVS 里保存的密码是空的 ***
```

## R-40 WiFi 连不上的真正根因：空密码被当成"已保存密码"

### 现象

扫描正常、<WiFi名称> 在列表里、信号也够，但一直 `reason 210`（`NO_AP_FOUND`）。

### 根因链

```
NVS 里 <WiFi名称> 的密码是空串（pass_len=0）
        ↓
wifi_mgr_saved_pass("<WiFi名称>") 返回指向 "" 的非 NULL 指针
        ↓
cc_ap_row_click_cb 里 if (saved != NULL) 成立 → 走"用已保存密码连接"
        ↓
wifi_mgr_connect("<WiFi名称>", "") → 空密码连 WPA2 → 210
        ↓
永远不弹密码输入框，用户怎么点都连不上
```

空串的**最初来源**是密码框：`pw_connect_cb` 不校验空输入，直接
`wifi_mgr_connect(ssid, "")`，而 `cred_put()` 会把空串写进 NVS **覆盖原密码**。
一次误操作（空着点"连接"）就永久毁掉这条凭据，且此后不再弹框。

> 注意：`auth=3` 是 `WIFI_AUTH_WPA2_PSK`。若真连开放网络，空密码是正常的，
> 所以修复必须区分"开放网络"和"加密网络"，不能一刀切。

### 修法（三处）

1. `ui_shell.c` `cc_ap_row_click_cb`：`saved != NULL && saved[0] != '\0'`
   才用已保存密码，否则**弹密码框**（这是让用户能自救的关键）；
2. `ui_shell.c` `pw_connect_cb`：空密码直接拒绝 + toast「请输入 WiFi 密码」，
   不再把空串写进 NVS；
3. `wifi_mgr.c` `wifi_mgr_connect`：防御性——传入空密码、但 NVS 有非空密码、
   且该网络在扫描结果里是加密的，就沿用已保存的密码并打警告。
   （排除开放网络，避免同名 SSID 从加密变开放时被旧密码干扰。）

### 验证

代码已烧写。**待用户操作**：点顶部状态栏 → WiFi 列表 → <WiFi名称> → 现在会弹密码框 →
输入正确密码 → 应能连上并拿到 IP。

## R-41 「以前明明能连上」的成因：加密方式未知被当成开放网络

### 用户问题

> 之前我就连接上了 <WiFi名称>，为什么会出现连接不上的情况？

### 结论

密码当时是对的（所以能连上），后来被设备自己**覆盖成空串**了。触发点是最普通的一个操作：
在控制中心点一下 <WiFi名称>。

### 代码层面的完整链路

`ui_shell.c` 构建 WiFi 列表行时：

```c
s_row_auth[idx] = 0;                    // 0 == WIFI_AUTH_OPEN
wifi_mgr_ap_info_t aps[16];
int n = wifi_mgr_get_scan_results(aps, 16);
for (int k = 0; k < n; k++) {
    if (strcmp(aps[k].ssid, ssid) == 0) {
        s_row_auth[idx] = aps[k].authmode;   // 只有扫到了才会被纠正
        break;
    }
}
```

`"已保存的网络"` 这一行**不依赖扫描结果**（刚开机、扫描还没回来时它也会显示）。
这时 `n == 0` 或该 SSID 不在前 16 条里，`s_row_auth` 就**保持 0 = 开放网络**。于是：

```
点 <WiFi名称>
  → s_row_auth == WIFI_AUTH_OPEN 成立
  → wifi_mgr_connect("<WiFi名称>", "")        // 空密码
  → cred_put("<WiFi名称>", "")                // 空串写进 NVS，覆盖原密码
  → 开机用空密码连 WPA2 → reason 210 (NO_AP_FOUND)
  → wifi_mgr_saved_pass() 返回指向 "" 的非 NULL → 永远不弹密码框
```

第 3 步是致命的：**一次点击就把密码永久毁了，而且毁掉之后界面再也不会给你补救的机会**。
这就是"以前能连、后来怎么点都连不上、也不弹密码框"的完整解释。

### 修法

| 位置 | 改动 |
|---|---|
| `ui_shell.c` `ap_add_row` | 默认值从 `0`（开放）改为 `0xFF`（未知） |
| `ui_shell.c` `cc_ap_row_click_cb` | 只有拿到**确切的** `WIFI_AUTH_OPEN` 才用空密码；未知值走"用已保存密码 / 弹密码框" |
| `wifi_mgr.c` `wifi_mgr_connect` | 传空密码时，只要 NVS 里有非空密码就沿用，**不再看扫描结果的 authmode**（那个值本来就可能是未知的） |
| `ui_shell.c` `pw_connect_cb` | 空输入直接拒绝（R-40 已加） |

### 实测验证（冷启动一次完整链路）

```
W ipcam: reset reason: 1(掉电/复位键) | 累计启动 109 次 / 异常 105 次
I wifi_mgr: band mode: 2.4G + 5G
I wifi_mgr: scan done: 5 unique AP(s)
I wifi_mgr: target "<WiFi名称>" ok: ch=11 rssi=-38 auth=3 -> connect
I wifi_mgr: got ip: <设备IP>  (RTSP: rtsp://<设备IP>:554/stream)
I ui_weather: weather updated: 深圳 20.1C code=3 daily=4 hourly=5
I ipcam: [heartbeat] up=34s wifi=已连接 ip=<设备IP> heap_int=105 KB (min 13 KB)
```

- 0 次 assert / 0 次 panic；
- 重启后 **自动**用已保存密码连上（无需再手输）；
- 天气自动拉到 20.1℃ / 4 天预报 / 5 小时逐小时；
- 信道 11、RSSI -38 dBm，信号良好。

> 注：`异常 105 次` 是调试期间累计的历史计数（含我自测时故意触发的那几次 panic），
> 不是当前状态；清零阈值是 500，下一次改动会顺手把 `rst_ver` 提到 4 触发一次归零。

## 附带发现：R-01 冷启动偶发崩溃（非本次改动引入）

抓日志时撞到一次冷启动崩溃：

```
rst:0x1 (POWERON), boot:0x30f (SPI_FAST_FLASH_BOOT)
entry 0x4ffac2d8                              ← bootloader 入口
Guru Meditation Error: Core 0 panic'ed (Instruction access fault)
RA: rtc_clk_init (rtc_clk_init.c:118)          ← 崩在时钟初始化
```

即 `DEVELOPMENT.md` 里记录的 **R-01**：发生在 bootloader、app 尚未执行。

- 与本次 WiFi / 天气改动无关（PC 在 ROM，早于任何 app 代码）；
- 当前配置 `CONFIG_SPIRAM_SPEED_200M=y` + `CONFIG_SPIRAM_FETCH_INSTRUCTIONS=y`，
  200MHz PSRAM 在冷启动时的时钟/时序是首要嫌疑；
- 建议 A/B：PSRAM 200M → 80M、flash 80M → 40M，各做 20 次拔插上电统计。
